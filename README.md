# MD1RoBoT 🧬

**محرك تطور ذاتي متعدد اللغات يعمل محلياً بالكامل، بدون أي واجهة خارجية مدفوعة.**  
يحلل الكود، يقترح تحسينات، ويطبقها تلقائياً عبر حلقة تطور مستمرة، باستخدام نماذج ذكاء اصطناعي محلية وأدوات فحص مفتوحة المصدر.

---

## 🎯 الهدف

نظام **Agentic Evolution** قادر على تطوير أي مشروع برمجي بأي لغة (أو مزيج من اللغات).  
يعتمد على نماذج محلية عبر **Ollama**، وأدوات تحليل ثابت ومترجمات حقيقية لتقييم موضوعي.  
يعمل داخل حاوية Docker واحدة تشمل كل شيء (Rust + Ollama + أدوات اللغات).

---

## 🧠 الفلسفة

كل تعديل يمر بدورة صارمة، وليس مجرد “جرّب وشوف” عشوائي:

```
ملاحظة → فرضية → طفرة → تجربة → تقييم → معرفة
```

النتائج الناجحة تتراكم كمعرفة قابلة لإعادة الاستخدام عبر مشاريع مختلفة، وليس كسجل تصحيحات منفصل.

### أدوار الشخصيات داخل النظام
| المكون | الدور |
|--------|-------|
| **Crazy** | مولد الطفرات: يقرأ المشروع ويقترح 3-5 تعديلات بأساليب مختلفة، مع قيد "Scope Guard" (لا يمس أكثر من 15% من الملفات في الدورة) |
| **Kreza** | المقيّم العدائي: يبحث عن الأخطاء، مشاكل الذاكرة، والثغرات، ويصدر حكماً (Approve / Reject / Modify / NeedsExperiment / Rollback) |
| **Seed** | الباحث: يجلب معرفة من الويب، ويتطور لاحقاً للبحث في GitHub Issues/PRs |
| **Planner** | مدير الدورة: ينسق بين المكونات، يحفظ نسخاً احتياطية، ويطبق أفضل طفرة |
| **ModelRouter** | يختار النموذج الأمثل حسب اللغة ونوع المهمة (حالياً Qwen2.5-Coder / DeepSeek-Coder) |
| **EvolutionLab** | بيئة تجارب: نسخ مؤقت، تطبيق التعديل، بناء/تشغيل، وقياس الأداء |

## 🔁 دورة التطور (Evolution Loop)

1. **بناء السياق** – تجميع حالة المشروع (جيل، لياقة، أهداف، موارد) عبر `ContextBuilder`.  
2. **توليد الطفرات** – `Crazy` يقترح 3-5 تعديلات باستخدام النموذج المحلي المناسب.  
3. **التجارب المختبرية** – `EvolutionLab` ينسخ المشروع، يطبق التعديل، يبني ويختبر، ويجمع بيانات الأداء (وقت البناء، نسبة الأخطاء، الذاكرة).  
4. **التقييم** – `Kreza` يحلل النتائج ويصدر حكماً بناءً على تحليل واقعي + استشارة نموذج لغوي عند الحاجة.  
5. **تطبيق أفضل طفرة** – `Planner` يحفظ نسخة احتياطية، يدمج التعديل، يسجل في قاعدة البيانات، ويحدّث الجيل.  
6. **بحث اختياري** – `Seed` يثري المعرفة إذا لزم الأمر.  
7. **العودة إلى الخطوة 1** – الدورة تتكرر آلياً.

## 🧠 النماذج المحلية والتوجيه

- **النماذج الحالية المُستخدمة:**
  - `Qwen2.5-Coder` (7B) – Python, JavaScript, TypeScript.
  - `DeepSeek-Coder` (6.7B) – Rust, C, C++, الخوارزميات.
- **التوجيه الذكي:** يختار `ModelRouter` النموذج بناءً على امتداد الملف ونوع المهمة وحجم السياق.
- **إدارة Ollama:** النظام يشغّل خادم Ollama داخلياً في الحاوية. تأكد من عدم تشغيل خادم آخر على نفس المنفذ (11434) لتفادي التعارض.

### الخطة المستقبلية – نظام المجلس (Council)
- تخصصات وعائلات (performance-family, security-family, style-family).
- اقتصاد طاقة: تكلفة رقمية لكل نموذج، فلا يُستدعى النموذج المكلف لمهمة بسيطة.
- سلاسل احتياطية (fallback chains) عند عدم توفر نموذج معين.
- دمج نماذج مستقبلية مثل GLM-5.2، Kimi K3، DeepSeek V4.

## 🚫 القيود الجوهرية (غير قابلة للتجاوز)

- ❌ **ممنوع** أي تعديل يستهدف تعطيل أو حذف الوحدات الأساسية (`main.rs`, `resource_governor.rs`, `evolution_lab.rs`).
- ❌ **ممنوع** أي محاولة استنساخ أو نشر ذاتي على خوادم خارجية.
- ❌ **لا Abliteration** على النماذج الأساسية المستخدمة في `Brain` أو `Kreza` – التوجيه الهندسي الصارم (system prompt محكم) بديل آمن وفعّال.
- ⚠️ النظام مصمم للتشغيل في بيئة معزولة. لا يُنصح بتشغيله على مشاريع إنتاجية دون مراجعة بشرية.

## 🗺️ خارطة الطريق (Roadmap)

### ✅ المرحلة الحالية – Genesis Core v8
- دورة تطور أحادية اللغة (Rust) عاملة بالكامل.
- توجيه نموذجي بسيط بين Qwen2.5-Coder و DeepSeek-Coder.
- تقييم واقعي + استشارة نموذج لغوي.

### 🔜 المرحلة 1 – الأساس المعرفي
- `theory_bank.rs` فوق `memory.rs`: تخزين نظريات معممة بدلاً من كل patch منفصل.
- ذاكرة نسيان دورية تزيل النظريات ضعيفة الثقة/عدد التجارب.
- مثال: "إزالة generic allocations تحسن وقت البناء لمشاريع Rust > 150 ملف – ثقة 91%".

### 🔜 المرحلة 2 – نظام القرار الجماعي (Council)
- **مجلس متعدد النماذج**: نموذج معماري كبير يقترح، نموذج سريع يكتب، نموذج مدقق يراجع.
- **اقتصاد الطاقة**: تكلفة رقمية لكل نموذج (مثلاً Qwen=1, Gemma=2, DeepSeek=6).
- **سلاسل احتياطية**: دعم نماذج بديلة، مع إمكانية التبديل الساخن (hot-swap) دون إيقاف الدورة.
- **نظام Tiers**: Fast / Balanced / Heavy حسب حجم المهمة والموارد المتاحة.

### 🔜 المرحلة 3 – تقييم أعمق
- **Kreza بثلاثة محاور:**  
  - اللياقة (Fitness) – هل نجح البناء والاختبارات؟  
  - السلامة (Safety) – وصول لملفات خارج المشروع؟ أوامر خطرة؟  
  - الأناقة (Elegance) – هل الكود الجديد أبسط وأكثر وضوحاً؟
- **تحليل AST حقيقي** عبر مكتبة `syn` بدلاً من مطابقة نصية.
- **صيغة قرار موزونة:** `Score = 0.4×Benefit + 0.2×Novelty − 0.2×Risk − 0.2×Cost`.
- **تقييم استقرار إضافي:** قياس الانحدار (regression) واستهلاك الموارد.

### 🔜 المرحلة 4 – عزل حقيقي و Kill Switch
- **عزل Docker كامل**: بدون شبكة، نظام ملفات للقراءة فقط عدا مجلد المشروع.
- **حدود صارمة:** `max_mutations_per_hour`، تسجيل كامل في `evolution_log.jsonl`.
- **Rollback معرفي:** عند فشل متتالي، يعود النظام لآخر نظرية ثابتة في `theory_bank.rs` وليس فقط لآخر commit.
- **Canary deployment داخلي:** تجربة الطفرة على نسخة فرعية قبل الدمج الكامل.

### 🔜 المرحلة 5 – بحث وتوسع
- **Seed V2**: البحث في GitHub Issues/PRs لمشاريع مشابهة.
- **Dream Mode**: وضع تحليل ذاتي مفتوح كل 24 ساعة بدون هدف محدد.
- **Vector Store معرفي**: تخزين المعرفة المستخرجة في قاعدة متجهات محلية (LanceDB/Chroma) مع ربطها بالسياق.
- **Tree-of-Thought / ReAct**: استخدام أساليب استدلال متقدمة في المطالبات مع النماذج القوية.

### 🧪 مؤجّل (لما يثبت الأساس)
- شجرة سلالات بفروع متخصصة (Rust-branch, distributed systems-branch) وتبادل جينات بينها.
- دعم كامل للغات TypeScript, Go, Java.
- دمج `llama.cpp` لتشغيل النماذج بدون Ollama خارجي.
- نظام تنافسي حقيقي: Crazy vs Kreza كفريقين منفصلين يتنافسان.
- **Distillation**: تدريب نموذج تلميذ صغير من أفضل النتائج.
- Abliteration بحذر على نماذج منفصلة مع الحفاظ على قيود الأمان البرمجية.
